# PISTE Studio V0.29 — Timeline Core Reliability

## Objectif

V0.29 durcit le noyau temporel et magnétique de PISTE Studio sans remplacer
la Storyline existante ni modifier le format public des projets.

Le chantier fait suite à l'audit comparatif de PISTE Studio avec plusieurs
éditeurs open source. Les principes utiles ont été réimplémentés dans
l'architecture PISTE ; aucun code tiers n'a été copié dans cette version.

## V0.29.1 — Integer Timebase

Le moteur dispose désormais d'un timebase interne entier à **1 MHz** :

- 1 seconde = 1 000 000 ticks ;
- conversion secondes → ticks via `Decimal(str(value))` ;
- calcul rationnel des positions de frames ;
- absence d'accumulation de flottants lors des reflows répétés ;
- conversion vers les secondes uniquement aux frontières publiques.

Les fichiers timeline continuent à exposer des secondes afin de conserver la
compatibilité avec les projets existants.

## V0.29.2 — Canonical Storyline Kernel

Une surface unique, `apply_storyline_operation`, porte les mutations
magnétiques canoniques :

- move ;
- trim ;
- connection point ;
- attach / detach ;
- insert ;
- remove ;
- reflow.

L'API locale expose cette surface via `POST /api/storyline/operate`.

Chaque opération passe par :

```text
timeline courante
→ validation
→ opération Storyline canonique
→ validation du résultat
→ vérification des locks
→ timeline candidate
```

Le backend devient ainsi l'autorité des règles de Storyline lorsque
l'application est connectée.

## V0.29.3 — Backend-authoritative gestures

Les gestes principaux de l'interface délèguent leur mutation au kernel
backend :

- reorder par drag ;
- ripple trim IN / OUT ;
- changement de parent ;
- déplacement graphique du point de connexion ;
- réglage numérique du point de connexion.

Le JavaScript conserve le calcul de preview nécessaire au feedback immédiat,
ainsi qu'un fallback pour le mode navigateur autonome. Il n'est plus la source
de vérité de la mutation lorsque le backend est disponible.

## V0.29.4 — Insert / Remove & Lock Safety

L'insertion et la suppression d'un plan STORY utilisent également le kernel
backend.

Les changements de présence sont désormais contrôlés par
`validate_locked_change` :

- ajout/suppression VIDEO → sémantique `reorder` ;
- titre → `graphics` ;
- audio → `audio_change`.

Les HARD/SOFT LOCKS existants restent donc compatibles sans introduire une
nouvelle famille de règles.

## Compatibilité

- timeline schema : **v6 inchangé** ;
- champs publics temporels : secondes inchangées ;
- anciens projets : compatibles ;
- `start` reste sérialisé pour compatibilité, mais les opérations magnétiques
  reconstruisent les positions de la STORYLINE à partir de l'ordre et des
  durées ;
- checkpoints persistants et Undo existants conservés ;
- aucune modification du Canon ;
- aucune modification du MASTER.

## Tests

La V0.29 ajoute des tests dédiés pour :

- bruit flottant `0.1 + 0.2` ;
- cadences rationnelles ;
- reflow de 100 segments sans dérive ;
- normalisation du validateur ;
- dispatch canonique move / trim / insert / remove / connexion ;
- endpoint Storyline ;
- délégation UI vers le backend ;
- blocage HARD LOCK sur insertion et suppression.

## Suite

La prochaine étape structurelle prévue est le **Transaction Journal** :
transactions de geste, coalescing et Redo, tout en conservant les checkpoints
persistants comme filet de sécurité. Son numéro de version sera vérifié contre
l'état réel du dépôt avant création.
